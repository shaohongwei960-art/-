> 历史参考：当前方向请看 [v0.2 简化版](产品方案-v0.2-简化版.md)，本版不再作为第一版功能清单。

> 暂用项目名：「换换」——仅为讨论代号，未核验商标、域名和应用商店重名情况。

## 一、产品结论

### 1. 一句话定位

**一个以双方自愿为前提，让闲置物品通过实物交换重新发挥价值的生活平台。**

用户能够像逛购物平台一样浏览物品，但不是付款购买，而是拿出自己的闲置提出交换。是否值得交换，由双方决定，平台不强制估价，也不承诺任何物品的真实性或市场价值。

### 2. 第一版建议

- **方式：** 同城、实物对实物、当面交接，不收现金差价。
- **人群：** 在一个有稳定生活联系的社区或片区，先服务有闲置、也愿意接受二手物品的成年用户。
- **品类：** 普通书籍、非电器家居小物、非安全关键的运动与户外用品；试点再缩小到其中两三类。
- **范围：** 一个地区内先形成足够密度，不一开始全国铺开。
- **形态：** 产品按移动端 APP 设计；验证阶段可用移动网页或适合目标市场的小程序测试，不必先做两套原生 APP。
- **原则：** 安全、举报、基本匹配和基本交换能力不付费；不做购买、竞价、充值和提现。

### 3. 什么借鉴电商，什么必须重做

| 可借鉴的电商体验 | 交换平台需要重新设计的机制 |
| --- | --- |
| 搜索、分类、筛选、收藏、清晰物品卡片 | 按“我想要什么”和“对方想要什么”双向匹配 |
| 物品详情、用户资料、消息通知 | 用“选择我的闲置并发起提议”替代加入购物车和付款 |
| 清晰的履约记录和售后入口 | 没有统一成交价，需要保存双方确认的交换条件 |
| 流畅的发布与浏览 | 同一件实物只能履行一笔交换，必须防止重复承诺 |

视觉和品牌应原创，而不是复制亚马逊的标识、页面或文案。

## 二、目标用户、需求与定位边界

### 1. 优先用户

| 用户 | 典型动机 | 核心顾虑 | 产品回应 |
| --- | --- | --- | --- |
| 社区整理型用户 | 家里有闲置，希望换到真正用得上的东西 | 沟通麻烦、见面不安全 | 引导发布、结构化提议、公开地点交接 |
| 兴趣轮换型用户 | 看完书、换一种轻量运动或兴趣 | 找不到愿意互换的人 | 愿望清单、同类推荐、双向匹配 |
| 搬家整理型用户 | 希望减少闲置并获得少量所需物品 | 时间紧、物品多 | 多件换一件、清楚的有效期；但不把紧急清空作为首要场景 |

优先选择前两类。急于清空的人未必还想获得其他东西，其需求可能更适合赠送或回收，不能假设所有闲置用户都适合交换。

### 2. 不优先服务

- 需要立即变现的卖家。
- 依赖标准定价和大量库存的专业商家。
- 希望快速处置贵重、专业鉴定类物品的人。
- 要求全国寄送或平台保证等价的人。

### 3. 核心需求表述

> 当我有一件仍可使用、但自己不再需要的东西时，我希望在附近找到愿意用我需要的物品与我交换的人，并以可控的时间和风险完成交接。

### 4. 差异化，不只是不收钱

1. **围绕物品的用途和偏好匹配，而不是围绕价格排序。**
2. **交换提议结构化，避免聊天半天仍不知道对方拿什么来换。**
3. **保存双方确认的具体物品、瑕疵说明和交接约定。**
4. **优先形成可实际见面的本地交换网络。**

“环保”和“有趣”可以作为品牌表达，但不虚构减碳数值，也不把它们当作已被验证的留存原因。

## 三、核心产品机制

### 1. 发布物品

一条发布记录代表一件真实物品，或一个明确不可拆分的组合。首版不做多库存商品。

必填信息：
- 标题、分类、实拍照片至少 1 张。
- 品牌或型号按品类选填；文字说明和已知瑕疵必填，无已知瑕疵也需主动声明。
- 成色：近新／使用良好／有明显使用痕迹，并提供文字定义，不能只用“九成新”。
- 粗粒度所在区域，不公开门牌号和持续实时位置。
- 想换的类别或关键词；也可选“愿意看看其他提议”。
- 是否接受对方用多件物品来换。
- 发布者确认有权处置该物品，且符合当地法律及平台规则。

鼓励补充：尺寸、配件、使用时长、可见面的时间范围。不得强制填写购买价格或上传含有地址等隐私的购买凭证。

发布前显示简短自检：拍清瑕疵、移除照片中的地址和人脸等不必要信息、不发布禁止交换物品。

### 2. 发现与匹配

提供三种入口：
1. **逛一逛：** 按分类、区域、发布时间、成色筛选。
2. **寻找想换的：** 搜索物品，并查看对方的愿望。
3. **双方可能合适：** 对方有我想要的物品，而我的可交换闲置又符合对方表达的需求。

首版采用可解释的规则，不需要先训练复杂模型：
- 硬过滤：已下架、已交换、被审核限制、被拉黑关系中的物品不推荐；已锁定物品不可发起新提议。
- 排序优先考虑双方需求命中，再考虑区域接近、物品信息完整度和近期活跃。
- 匹配提示写“你有他想换的书籍”，而不是未经验证的“成交概率 95%”。
- “接受其他提议”代表开放，不等于对所有物品都感兴趣。
- 精确位置不参与对外展示；优先使用区域匹配，不强求定位权限。

未发布物品的用户仍能浏览与收藏，但首页不能伪装成已有个性化双向匹配；发起交换时再引导发布自己的物品。

### 3. 发起交换

用户在物品详情点击 **“用我的闲置换”**：
1. 选择自己 1—3 条可交换物品记录。
2. 对方目标为 1 条物品记录；首版不支持双方同时选择多条的复杂组合。
3. 查看双方物品、瑕疵说明和“无现金补差”提示。
4. 写一句提议理由，选择大致可交接区域。
5. 确认后发送，对方可以接受、拒绝或聊天协商。

同一组物品向同一对象只能有一条有效待回复提议；设置可配置的每日发送限额及异常频率控制，防止骚扰。

提议默认 7 天未接受则失效，发起者可在接受前撤回。有效期属于试点参数，可根据真实回复周期调整。

### 4. 接受与锁定

**发送提议即代表发起者同意该版本的交换条件；接收者接受时形成双方确认。**

- 接受动作必须再次检查：物品仍可交换、版本未变、双方账户状态正常。
- 通过一个原子事务锁定涉及的全部物品，任何一件无法锁定，整笔接受失败，不能部分成功。
- 未接受前允许一件物品收到多条提议，但接收提议不代表承诺履约。
- 一笔提议被接受后，关联物品的其他提议标记为“暂不可接受”；原有效期继续计时。
- 取消后，仍有效且条件未变的其他提议恢复可接受；完成后，它们自动失效并通知相关用户。

**编辑保护：** 待回复期间，如果照片、成色、瑕疵、组成或愿望等交易相关信息变化，旧提议失效并通知对方重新确认。接受后物品资料只读；改变交换物品必须取消并重新发起，不能只在聊天中改掉已确认的内容。

### 5. 交接与完成

1. 接受后进入“待约定交接”。
2. 双方确认公开交接地点与时间；一方提出修改，另一方需再次确认。
3. 48 小时内未共同确认交接安排，系统提醒并到期取消、解锁；双方可以在到期前共同延期一次。
4. 到场后检查实际物品、配件和瑕疵；不满意可以不换，不得强迫交付。
5. 实际交付后，双方分别点击“我已完成交接”。
6. 双方均确认后记录为完成，物品转为已交换，开放互评。

接受、聊天或扫码见面都不能替代实际完成确认。扫码只可辅助核对双方，首版不必实现。

**不自动假定完成：** 约定时间经过但无人确认时，先提醒并允许声明未发生交接；仍无响应的交换进入异常处理。只要一方声明已交付或提出纠纷，物品就不能自动解锁，避免再次承诺已交出的物品。不得靠超时自动生成好评或伪造完成记录。

### 6. 取消与纠纷

- 无任何一方声明已交付且无纠纷时，任一方可取消，释放全部物品；记录原因，但不把一次取消等同于不诚信。
- 已有一方确认交付，另一方取消或长期未确认，进入“待核实”，不直接作废或完成。
- 出现描述不符、少件、损坏、爽约、骚扰等问题，可以从交换记录提交举报或纠纷。
- 支持双方协商取消、补充证据或自愿换回；平台不能凭空保证追回线下物品。
- 客服根据适用规则处理账户限制、内容下架及记录纠正，并提供申诉入口。涉及违法或人身风险时提示联系当地适当机构。

首版无托管、押金或保险，不承诺平台赔偿。若以后增加保障服务，需要独立规则、资金来源和当地合规评估。

## 四、状态机与一致性规则

### 1. 物品状态

`草稿 → 待审核 → 可交换 → 已锁定 → 已交换`

补充分支：审核不通过、主动下架、违规下架。取消交换可使“已锁定”恢复为“可交换”，但仍须满足审核和账户条件。

### 2. 提议与交换状态

`待回复 → 已接受 / 待约定 → 待交接 → 单方确认 → 双方确认完成`

其他出口：
- 待回复 → 已拒绝／已撤回／已过期／因资料变化失效。
- 已接受、待交接 → 已取消，或因安全事件进入待核实。
- 单方确认 → 对方确认完成，或进入待核实。
- 待核实 → 根据双方声明和处理结果完成、取消或结案但结果无法确认。
- 完成后仍可发起售后纠纷，保留原完成事件及后续处理记录，不悄悄删除历史。

### 3. 必须满足的产品规则

- 一条物品记录最多属于一笔进行中的已接受交换。
- 多件换一件的锁定、解锁和完成必须整体处理。
- 重复点击、网络重试不能生成重复提议、重复完成或重复通知。
- 保存双方接受时的物品快照、条件版本、确认时间和状态日志。
- 锁定期间不能删除或修改核心物品资料；可以举报，由平台安全处置。
- 拉黑不抹除已接受交换；安全举报可冻结直接沟通，转客服完成取消或纠纷处理。
- 账户注销不得绕过未结交换与争议；注销、保留及删除期限按适用规则设计。

## 五、信息架构与页面方案

底部导航建议：**首页｜交换｜发布｜消息｜我的**。

| 页面 | 主要内容 | 主操作 |
| --- | --- | --- |
| 首页 | 搜索、区域切换、分类、附近新发布、双向匹配推荐 | 查看物品、筛选 |
| 搜索结果 | 关键词、区域、分类、成色、发布时间 | 调整筛选、收藏 |
| 物品详情 | 实拍、瑕疵、组成、想换什么、区域、发布者历史 | 用我的闲置换 |
| 发布页 | 分步填写物品与愿望，审核提示 | 发布、存草稿 |
| 发起提议页 | 我提供的物品与目标物品并列展示，规则摘要 | 确认发送 |
| 交换中心 | 收到的、发出的、进行中、已结束 | 接受、拒绝、查看记录 |
| 交换详情 | 条件快照、交接安排、状态时间线、安全提醒 | 约时间、确认完成、取消、求助 |
| 消息 | 围绕物品或提议的会话、系统提醒 | 沟通、举报、拉黑 |
| 我的 | 我的闲置、愿望、收藏、交换历史、评价、设置 | 管理物品与隐私 |
| 用户资料 | 昵称、粗略区域、完成次数、有效评价 | 查看其闲置、举报 |

### 关键交互细节

- 卡片突出 **“想换：……”**，不放价格和虚构估价。
- 无匹配时建议扩大区域、补充愿望或接受更多提议，不展示假的库存和交易。
- 对已锁定物品允许收藏，但禁用发起交换，并说明状态。
- 拒绝提议可选标准理由，如“不符合目前需求”，不强制解释。
- 核心会话围绕物品或提议创建，不开放无限制陌生人私信。
- 举报和退出流程保持易找；不以连续弹窗阻止用户拒绝交换。
- 图片加载失败、网络断开、提交重试、定位拒绝和空列表都应有明确反馈。
- 兼顾大字体、读屏标签、足够对比度和非颜色状态提示。

## 六、MVP 范围与优先级

### P0：受控试点前必须具备

- 注册登录、基本账户管理、成年用户准入声明、条款与隐私告知。
- 发布、审核、编辑、下架、图片上传与瑕疵说明。
- 区域选择、搜索、分类筛选、收藏。
- 愿望类别、简单规则匹配及匹配原因。
- 发起、接受、拒绝、撤回、过期及关联提议处理。
- 物品原子锁定、条件快照、状态日志。
- 站内文字／图片消息、消息反骚扰与系统通知；图片同样需要举报和审核能力。
- 双方确认交接安排、双向完成确认、取消与异常入口。
- 完成后互评、举报、拉黑、申诉。
- 运营后台：内容审核、举报队列、纠纷记录、账户限制、操作审计。
- 核心漏斗埋点、权限隔离、限流、备份与恢复验证。

### P1：试点证明需求后再做

- 更细的愿望清单、保存搜索、合适物品到达提醒。
- 类别属性模板、模糊检索、个性化排序。
- 自愿参加的社区交换活动、非实时公开交接点信息。
- 更精细的通知、爽约申诉和运营工具。
- 符合当地规则的可选认证；明确只核验什么，不暗示可信度保证。

### P2：单独评估后决定

- 异地邮寄、物流及丢损争议机制。
- 平台保障、托管或商业保险。
- 双方多件组合交换、社区组织者工具。
- 三方循环交换、专业品类鉴定。

### 明确不进入首版

现金交易、现金补差、可购买或提现的积分、拍卖、全国寄送、三方链式交换、直播、信息流社交、平台自动估值、未经审核的商家批量上架。

**特别说明：** 积分虽然能缓解双方需求不匹配，但会引入发行、兑换、公平性、刷分和潜在金融合规问题。它不是一个可以随手添加的“小功能”。

## 七、信任、安全与隐私

### 1. 首版限制品类

除当地法律禁止的物品外，试点主动排除：武器及危险品、药品和医疗器械、酒精烟草、食品及保健品、宠物和其他活体、账号与证件、现金及金融资产、疑似赃物和假冒物品、召回或失效物品。

为降低履约和健康风险，首版还不接受高价值珠宝奢侈品、手机电脑等高价值电子产品、存在电气风险的电器、儿童安全座椅、防护头盔、攀登防坠器材及贴身卫生用品等。正式禁限清单须按地区、实际运营能力和法规审核。

### 2. 安全默认值

- 面向成年人；成年声明不等同于年龄核验，公测前评估当地年龄核验要求。
- 地图与列表只展示粗略区域；精确交接地点仅在已接受交换中向双方展示。
- 建议白天、人流较多的公共场所交接，不要求到家，不默认公开手机号。
- 不强制授权通讯录、持续定位或上传身份证照片。
- 图片处理去除 EXIF 等不必要的定位元数据。
- 消息提示防范订金、保证金、运费预付、外部支付链接和索要验证码等行为。
- 发现人身安全风险时，允许立即停止交接和联系适当机构，不以完成率约束用户。

### 3. 信用机制

首版不做不可解释的“综合信用分”，而展示可理解的信息：
- 注册时长。
- 双方确认的完成次数。
- 完成后的有效互评与文字反馈。
- 用户选择展示的认证及其准确含义。

仅完成交换的双方可以互评，一人一条，可举报。建议采用双盲评价：双方提交后公开，或评价窗口 7 天结束后公开已提交评价；窗口是可调参数。未交换成功不开放交易星级评价，但可以私密反馈爽约或骚扰，由平台核实。

不公开未经核实的“骗子”等标签，不将身份核验等同于商品鉴定或履约保证。

### 4. 数据与后台权限

- 只收集账户、物品、愿望、粗略地区及履约所必要的信息。
- 明确说明聊天和证据在何种举报、审核或支持场景下可被授权人员查看。
- 后台按角色授权，访问敏感资料和修改交换状态均记录审计日志。
- 对外隐藏联系方式；上传证据引导遮盖无关个人信息。
- 提供账号删除和相关隐私请求入口；公开展示下架与内部依法留存分别处理。
- 具体保存期限、跨境传输、服务提供商和删除策略在选定上线地区后形成正式政策。

**无现金不等于无责任。** 仍需评估消费者权益、产品安全、税务、隐私、平台审核及本地线下活动责任等适用要求。

## 八、运营与冷启动

### 1. 先解决密度，而不是下载量

交换需要同时满足区域、需求和可提供物品三个条件。全国分散的许多注册用户，未必比同一社区少量认真发布的用户更有用。

建议试点选择一个社区、办公园区或成年兴趣群体，满足：
- 有明确组织者或招募渠道。
- 有适合公开交接的公共空间。
- 用户之间存在一定生活联系，但不要求相互认识。
- 有固定运营人员处理审核、反馈与纠纷。

### 2. 招募示例

以 **50—100 位成年种子用户、每人 2—3 件真实闲置** 作为可管理的实验规模，而不是行业基准或成功保证。

流程：
1. 先征集“手上有什么”和“最近想要什么”。
2. 选择供给和愿望有一定交集的两三类物品。
3. 帮助用户补充照片、瑕疵和想换的东西，但不能替他们虚假确认。
4. 定期整理合适的匹配，获得授权后进行人工推荐。
5. 可组织小型线下交换日，事先确认场地许可、安全与应急安排。
6. 对每笔失败交换记录主要原因，不只采访成功者。

### 3. 激励边界

可以使用非货币徽章、整理挑战或活动展示；不按完成次数直接发放可变现奖励，避免互刷。邀请奖励与未来付费推广也要防止虚假物品、骚扰和低质量增长。

人工撮合可以验证需求，但必须单独记录人工投入，否则容易把运营人员的努力误认为产品已经能自主匹配。

## 九、商业模式

### 1. 试点不急于收费

先证明用户愿意发布、可以获得有效提议、能够完成交接并愿意再次使用。没有这些证据，会员和广告难以形成可持续收入。

### 2. 可测试方向

| 方向 | 提供的额外价值 | 必须控制的风险 |
| --- | --- | --- |
| 增值订阅 | 更多保存搜索、高级整理工具、可选通知能力 | 不能把基础匹配和安全能力锁进付费墙 |
| 明确标记的推广位 | 帮助相关物品获得额外曝光 | 不冒充自然匹配，不让付费压倒相关性 |
| 社区或机构服务 | 活动管理、组织者工具、经许可的场地合作 | 参与者数据不能擅自提供给机构 |
| 后续第三方服务 | 可选物流、鉴定等服务对接 | 成本、责任、资质和佣金透明；不纳入首版 |

首版没有价格，按成交金额抽佣不适合作为默认模式。是否接受服务收费仍需要真实付费实验，而不是口头认可。

### 3. 成本与可行性

持续跟踪图片存储、消息通知、审核、客服、安全和获客成本。

`每笔确认完成的运营成本 = 当期相关运营成本 ÷ 当期确认完成笔数`

同时单独记录研发等固定投入、人工撮合时长和机构活动成本。没有付费测试前，不给出收入预测或盈利时间承诺。

## 十、指标体系与验证标准

### 1. 北极星指标

**每周双方确认完成、排除已识别作弊的有效交换笔数。**

这仍是用户确认口径，不等同于平台现场核验。完成后的纠纷、撤销和异常通过独立指标持续追踪。

### 2. 指标定义

| 指标 | 定义与用途 |
| --- | --- |
| 发布激活率 | 新注册用户中，7 天内发布至少一条审核通过物品的人数占比 |
| 提议覆盖率 | 发布后观察满 7 天的物品中，期间收到至少一条有效提议的比例 |
| 有效回复率 | 观察满 48 小时的提议中，48 小时内被接受、拒绝或获得实质回复的比例；不把系统消息当回复 |
| 提议接受率 | 已到期或已结束的有效提议中，被接受的比例；另报仍待回复数量，避免分母混杂 |
| 交换完成率 | 已接受交换中，在统一 14 天观察窗口内双方确认完成的比例；待核实单列，不隐去失败 |
| 首换时长 | 从首次审核通过发布到首次确认完成的时长；同时报告尚未完成者占比 |
| 30 天再次参与率 | 已首次完成且观察满 30 天的用户中，期间再次发布或发起提议的比例；再次完成率另报 |
| 安全护栏 | 举报率、爽约反馈率、完成后纠纷率、严重安全事件数及处理时长 |
| 人工依赖 | 人工协助交换占比、每笔完成所需人工分钟数 |

核心事件包括：发布提交／通过、搜索、详情浏览、发起提议、接受／拒绝、锁定失败、约定确认、单方／双方完成、取消、举报及评价。埋点应避免收集完整聊天正文和精确住址，并使用事件标识去重。

### 3. 试点决策，不只看热闹

建议观察至少 4—6 周，并确保主要指标有完整观察窗口。小样本首先报告人数和笔数，避免把两三笔结果包装成稳定百分比。

试点前可商定一组探索门槛，例如：
- 至少完成 20 笔双方确认、排除已知作弊的交换。
- 大部分完成不依赖运营人员逐笔劝说。
- 失败原因中有相当部分可以通过匹配、信息和流程改善，而不是用户根本不愿交换。
- 没有尚未处理的严重安全问题，运营团队能承受当前审核和支持工作量。

以上是讨论用门槛，不是市场基准；达到也不等于商业模式成立。

结果解释：
- **发布多、提议少：** 排查区域密度、愿望过窄、品类错配与展示问题。
- **提议多、接受少：** 排查不合适提议、物品描述、信任和交换意愿。
- **接受多、完成少：** 排查距离、约时间、爽约与交接流程。
- **完成多、复用少：** 排查闲置频率、需求是否已被一次满足和新的供给是否不足。
- **主要靠人工完成：** 先改匹配和流程，不急于增加城市。

## 十一、产品验证与研发路径

### 阶段 A：访谈与人工交换实验

建议 1—2 周作为初始时间盒，访谈约 15—20 位候选成年用户，并征集真实物品与愿望。

重点不问“你喜欢这个创意吗”，而问：
- 最近一次处理闲置是什么时候，实际怎么处理？
- 现在愿意拿哪件物品出来？有什么瑕疵？
- 最近真正需要什么？愿意接受什么成色？
- 为交换能走多远、等多久、花多少沟通时间？
- 面对一个具体交换提议，会接受还是拒绝，为什么？

安排少量真实、自愿的人工撮合，观察履约。若根本没有双方愿意接受的组合，优先调整人群与品类，而不是直接扩充功能。

### 阶段 B：可点击原型

建议 1—2 周时间盒，覆盖首页、详情、发布、提议、接受、交接、取消与举报。

用约 5—8 位目标用户做任务测试：能否不解释就理解交换机制，能否看出自己要交出什么，能否找到拒绝和退出入口。修正重大误解后再研发。

### 阶段 C：受控 MVP

在“一名产品／设计、一名前端、一名后端、共享测试和运营支持”的假设下，可先预留 **6—10 周** 作为粗略研发规划，随后按实际需求和团队能力重新估算。

这一估计针对移动网页或单一客户端的受控试点，不包含两套原生客户端、应用商店审核、复杂身份核验、当地法律评估、商业保障和全国运营。

开发顺序：
1. 账户、发布、审核、区域浏览。
2. 愿望、提议、快照、锁定及状态机。
3. 消息、交接、取消、异常、评价。
4. 后台、埋点、安全与完整回归测试。

### 阶段 D：单区域试点

至少安排 4—6 周观察。按周复盘漏斗、失败原因、审核成本与安全事件。未经这些验证，不承诺上线城市数量和下载目标。

预算待团队、地区、客户端与服务商确认后，按“开发人月＋持续基础设施＋审核客服＋法律与安全＋线下活动”拆分测算，而不是在需求未定时给出虚假精确报价。

## 十二、技术方案边界

本阶段不写代码，只给实现约束，避免原型演示掩盖履约问题。

### 1. 建议架构

- 移动端客户端，使用统一 API；试点优先响应式移动网页。
- 模块化单体后端，不先拆微服务。
- 关系数据库存放用户、物品、愿望、提议、交换、快照、状态日志和评价；使用事务与约束实现锁定一致性。
- 对象存储保存图片，限制类型、大小并进行安全处理。
- 后台任务处理提议过期、通知、审核队列与异常提醒，任务可重试且幂等。
- 初期使用数据库检索和规则匹配，出现明确瓶颈后再引入独立搜索引擎。
- 独立运营后台、分角色权限、审计与监控。

### 2. 核心数据对象

`用户 User`、`物品 Item`、`愿望 Wish`、`提议 Proposal`、`交换 Exchange`、`物品快照 Snapshot`、`交接安排 Handoff`、`消息 Message`、`评价 Review`、`举报 Report`、`争议 Dispute`、`审核日志 AuditLog`。

### 3. 最重要的非功能要求

- 任何人不能通过猜测 ID 读取别人的私信、精确交接地点或举报证据。
- 并发接受、重复请求和消息延迟不能破坏唯一锁定规则。
- 客户端按钮禁用不能替代服务端权限和状态验证。
- 通知失败不改变真实交换状态；用户回到交换详情能看到权威状态。
- 备份必须做恢复演练，错误日志不记录敏感正文和身份材料。
- 发生服务中断后可恢复未结束交换和状态记录。

## 十三、上线验收清单

| 场景 | 通过标准 |
| --- | --- |
| 用户无闲置时发起交换 | 被引导发布，不出现空物品提议 |
| 双方正常互换 | 发布→提议→接受→共同约定→双方完成→互评闭环可走通 |
| 多件换一件 | 任一物品不可用，整笔接受失败；不存在部分锁定 |
| 两人并发接受涉及同一件物品的提议 | 只能一笔成功，另一笔明确说明物品不可用 |
| 修改已被提议物品 | 旧条件失效并通知；不能按过期资料自动接受 |
| 重复点击或断网重试 | 不生成重复交换、不重复解锁、不重复完成 |
| 提议过期／拒绝／撤回 | 状态一致、不能再次接受，关联用户获知结果 |
| 接受后未约时间 | 按规则提醒、到期取消并整体解锁 |
| 一方确认交付，另一方不响应 | 不自动好评或解锁，能够进入待核实 |
| 取消与拉黑 | 不丢失已有记录；活动交换可安全退出或转客服处理 |
| 违规内容与危险用户 | 审核、下架、举报、限制、申诉和审计可追踪 |
| 隐私与权限 | 非参与人无法访问私信、交接地点或证据；图片无多余定位元数据 |
| 用户拒绝定位权限 | 可手动选择区域，正常浏览和交换 |
| 运营与恢复 | 有真实值守人员、明确支持时间，并通过一次备份恢复测试 |

对外公测前，补齐目标地区的规则审核、服务提供商评估、正式隐私政策和用户协议；明确平台不是紧急救援服务，不能虚假承诺 24 小时即时人工处理。

## 十四、主要风险与取舍

| 风险 | 早期应对 | 不能承诺的事 |
| --- | --- | --- |
| 双方需求很难正好匹配 | 密集社区、愿望标签、开放提议、多件换一件 | 上架后一定有人换 |
| 用户对“值不值”意见不同 | 展示条件、允许拒绝、禁止强迫成交 | 平台保证等价 |
| 虚假描述与失约 | 瑕疵必填、条件快照、当面检查、反馈和申诉 | 身份认证能消除欺诈 |
| 线下安全风险 | 成年试点、公开地点、隐私保护、异常处理 | 公共地点绝对安全 |
| 供给不足或低质量 | 聚焦人群品类、真实招募、持续运营 | 靠页面美观解决流动性 |
| 审核客服成本过高 | 缩小品类、明确规则、测量人工投入 | 全靠自动化处理纠纷 |
| 环保口号掩盖低频使用 | 观察真实再次发布和再次交换 | 用户喜欢理念就会长期使用 |

## 十五、尚需你确认的四个方向

当前默认值只是为了让方案可以继续，不代表已替你做最终决定。

| 决策 | 当前建议 | 会影响什么 |
| --- | --- | --- |
| 首发地区 | 先选一个你能组织种子用户的城市片区或社区，国家／地区未定 | 法律、语言、登录、地图、隐私、招募 |
| 第一批人群 | 成年社区用户或成年兴趣群体 | 品类、交换频率、安全和运营渠道 |
| 交换边界 | 实物直换、无现金补差、无积分、同城见面 | 规则复杂度、匹配效率、履约成本 |
| 第一阶段投入 | 先人工验证和可点击原型，再受控 MVP | 团队、预算、排期与客户端选择 |

## 最终建议

**保留“像电商一样好逛”的体验，但把第一阶段的成功标准定为“让同一个社区里的人，安全、清楚、自愿地完成真实交换”。**

不要先追求庞大的商品量、全国覆盖或复杂积分体系。先用真实闲置证明三件事：有人愿意拿出来、有人愿意拿自己的东西来换、双方真的愿意完成交接。下一步最有价值的成果是一个可执行的种子用户访谈与试点招募计划，然后再把验证后的规则转成页面原型。
